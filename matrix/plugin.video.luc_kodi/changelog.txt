[B][COLOR ff00fa9a]Version 1.0.85[/COLOR][/B]
[COLOR fffdb515]Dynamic range now reads as one thing in the source list[/COLOR]
-A file that carries a Dolby Vision layer over an HDR10 base was writing HDR and DOLBY-VISION as two separate pieces with a bar between them. That is the same fault the audio block fixed: they are not two things. They are one - the dynamic range of that file, which happens to have two layers - and they are now written as one.
-The order runs from least to most capable, so the row ends on the best that file can do, and the fallback is named first: on a device without Dolby Vision, HDR10 is the part that matters. Dolby Vision on its own stays alone, because a profile 5 file has no HDR10 fallback and saying otherwise would be a lie.
-HDR10+ no longer names its own base. There is no HDR10+ that is not also HDR10, so writing both said the same thing twice. Two spellings of the same format in one name also collapse into one label instead of appearing twice.
-A name that declares SDR and HDR at once contradicts itself. The impossible half is dropped rather than printed as a pair that means nothing.
-The profile and the layer stay outside the block. DV-P5, DV-P8 and FEL/MEL are the only highlighted items in that row, and for a reason: they decide whether the device can play the file at all. Inside the block they would lose both the accent and the leading position. Bit depth stays outside too - next to HDR it is redundant, but on an SDR file it is real information, and a 10-bit SDR encode is a common thing to meet.
[COLOR fffdb515]Inside a block, a dot instead of a bar[/COLOR]
-The vertical bar separates different things in the row. Inside a block there are no different things, so marking it with the same stroke said two different things with one sign. Inside it is now a dot: HDR10+ DOLBY-VISION, DTS-MASTER AUDIO TRUE HD (5.1).
-The dot is the Latin-1 middle point, which every interface font carries. The add-on ships no fonts of its own, so the glyphs available are whichever the user's skin provides, and the more decorative candidates are exactly the ones that come out as empty boxes on a stripped font. It is set in bold, which is the only control a Kodi label has over how heavy a character lands, and puts it about a quarter thicker than plain.
[COLOR fffdb515]Fixed: on a 4K interface the rule was measuring against the wrong background[/COLOR]
-The window backdrop is the fanart over black, faded to 25%. In the 2160p skin set that fade had been doubled to 50%, because the generator treats every number as a screen measurement - but the end of a fade is opacity, and opacity does not scale with resolution. The real backdrop was (61,61,61) there instead of (31,31,31).
-Everything the colour rule computes for that window is measured against that backdrop, so on a 4K interface all fourteen checks - the quality bar, the quality icon and the poster frame, plus the breakdown header - were sitting below their floor. The header fell from 4.6 to 3.0 against a floor of 4.5. Nothing reported it, because the rule was reading the value from the 1080 set.
-The same fault was one control away: the clearlogo zoom ended at 180% instead of 90%, so on a 4K interface the logo was drawn at double size, ran off the top of the screen and covered the first row and a half of the list. Zoom values are percentages too.
-Both are back to the master's values. Sweeping all twenty skin windows for fade, zoom and rotate animations, these were the only two that differed between the sets; everything else flagged was a slide, where doubling is correct.
[COLOR fffdb515]The focused card is darker, and the rule decided how much[/COLOR]
-The focused card was a mid grey typed by hand into four places across the two skin sets. On that paper the rule had to push the routine ink up to a near white, repeated the whole length of the line, just to reach the contrast floor. That is the glare that stings in a dark room.
-It is now darkened by the smallest amount that makes it a different paper rather than the same one slightly dirty: the same measurable distance the rule already demanded between two colours of the same family. That works out at 34%.
-Because the floor is reached sooner on darker paper, and the rule always takes the dimmest tone that passes, the text does not get brighter - it gets softer. The routine grey drops by a full step and still clears 4.0 against every card and every service tint, checked across all 56 combinations.
-The grey the skin paints and the background the ink is calculated against are now literally the same number: the colordiffuse comes from the rule instead of being written into the XML.
[B][COLOR ff00fa9a]Version 1.0.84[/COLOR][/B]
[COLOR fffdb515]Colour in the source list is now decided by a rule, not written by hand[/COLOR]
-Every colour in this window used to be a hex value typed somewhere: six for quality in the window code, the same six again in the poster frame, thirteen PNG files with the colour baked in, six for the debrid services, plus a fixed salmon for rare tags and a fixed aqua for the pre-flight figure. Over twenty places for what are really two families - and they had already drifted apart, with the 720p bar a different orange from its own card and the SCR bar a different red from its own.
-What is stored now is one hue per concept. The role that hue plays - ink, surface or signal - and the background it actually lands on decide everything else, each time a row is drawn. The poster frame, the quality bar, the quality icon and the row text all come from that single table, so they can no longer disagree with each other.
[COLOR fffdb515]The three conditions the rule has to meet[/COLOR]
-Legibility: any text colour must reach 4.0 contrast against the real composited background - window backdrop, quality card at 23.5%, debrid tint along its gradient - and not against a theoretical black.
-Comfort: of every tone that passes, the rule takes the dimmest rather than the brightest, and saturation is capped. The 4K cyan and the 720p amber sat at full saturation, which is what stings in a dark room.
-Identification: two colours in the same family must stay a measurable distance apart. Where two collide the rule reports it instead of quietly rotating a hue, because rotating the 4K cyan without saying so would be changing a design behind its author's back. The one collision found this way - 4K against SD, both in the same blue sector - is resolved by a declared exception that takes chroma off SD rather than moving either hue.
[COLOR fffdb515]Fixed: text was being painted in the colour of its own background[/COLOR]
-The card is tinted with the colour of the service that resolved the source, and the service name was then written in that same colour on top of it. On a Real-Debrid row that measures 1.74 contrast, which is not readable at all. Surface and ink are now two separate values, the second computed against the first.
-The focused row had the same fault from the other side: its card is mid grey and its text near black, which caps at 2.69 contrast however dark the text goes. No shade of dark ink can fix that, so the rule resolves the focused row to light ink.
-The focused row's tint was built from a substring expression that left seven characters of an eight-character colour, so it had never been a valid value. It has its own property now.
[COLOR fffdb515]The second row is down to two inks[/COLOR]
-Rare tags and the pre-flight bitrate no longer carry fixed colours of their own. Both take the accent of the row they sit on, which comes from the service that resolved that source - because that is what a row is. A row now holds an accent, a routine grey and a separator.
-The separator was full-saturation amber repeated six times per row, and was the loudest thing on the line. It is neutral now, and sits below the routine grey on purpose: it is punctuation, not information.
-Labels such as SCORE and SEEDERS were inheriting a brighter default colour than the values they label. They now match.
[COLOR fffdb515]Several audio tracks in one name are now one block, not two[/COLOR]
-A release carrying both DTS-HD MA and TrueHD was written as DTS-MASTER AUDIO (5.1) | TRUE HD - the channel count on the first track and the second one left stranded behind a bar, as though the two had nothing to do with each other. They describe one file's audio, so they are written as one thing: DTS-MASTER AUDIO/ATMOS-TRUE HD (5.1).
-Putting the channel count at the end of the whole block is also the more truthful place for it. A release name declares one channel count, not one per track. Attached to the first codec it claimed that track is 5.1 and said nothing about the rest; at the end of the block it says what the name actually says, which is that the audio is 5.1. What this still will not do is invent a count per track that the name never gave.
[COLOR fffdb515]Fixed: Atmos was being credited to the wrong codec[/COLOR]
-Atmos is a Dolby extension. It rides on TrueHD or on Dolby Digital Plus, and never on DTS. The row was attaching it to whichever codec came first in the list, so a name declaring DTS-HD MA, TrueHD and Atmos together produced ATMOS-DTS-MASTER AUDIO - crediting DTS with something that is not its own.
-It now attaches to the Dolby track that carries it, preferring TrueHD over Dolby Digital Plus when a name declares both. A name that claims Atmos with no Dolby codec under it gets Atmos as its own entry in the block rather than bolted onto whatever happened to be nearby.
[COLOR fffdb515]Scope[/COLOR]
-This covers the source results card and the poster frame beside it, and nothing else. The add-on's green identity colour is deliberately outside the rule.

[COLOR fffdb515]Three ways of writing things that were being missed[/COLOR]

Only genuinely new titles download their full details at start-up.
-NEW: "Full metadata refresh at most every (hours)" setting (default 12) in the TMDB Catalog Update section. The heavy cycle that re-downloads full details - cast, logos, alternative posters, certifications, trailers - still runs, but at most once per this interval instead of on every single start, and also during long sessions when the interval elapses. Nothing is lost: info dialogs keep exactly the same data as before, refreshed on a schedule rather than on every boot.
-CHANGE: Tools > "TMDB: Update Catalog (Precache)" is now a guaranteed full refresh - it re-reads the lists AND re-downloads full metadata immediately, whenever you want everything fresh without waiting for the schedule.
-FIX: the "Check interval (hours)" setting was read as its position in the list rather than the hours it displays, so "6" actually checked every 2 hours. Both interval settings now map to real hours.
-FIX: resume points were silently lost for any title whose name contains double quotes. The bookmark lookup and cleanup pasted the title straight into the database query, so a quoted title broke it (visible in kodi.log while merely scrolling a list containing such a title). Both queries are now parameterized, so any title resolves and stores its resume point correctly.
-FIX: playback failed with "Playback not supported" when the chosen release was packed as a multi-part archive. Parts such as .z01/.z03, .r00, .part01.rar or .001 were missing from the invalid-extension lists and, being huge, won the largest-file selection - so the player received a fragment of an archive instead of a video. A shared check now filters them out for Premiumize, AllDebrid and the AllDebrid cloud browser, and the real video file inside the release is picked instead. Legitimate video files, including .ts and .m2ts, are untouched.
-FIX: MDBList ratings were never applied to TV shows in the source-selection panel. The lookup always used the movie route, so for a series MDBList replied 404 and every rating slot it should have filled (IMDb, TMDB, Trakt, Letterboxd and the rest) was left to the slower fallback. The route now follows the media type, so shows and episodes get their MDBList ratings just like movies.
-FIX: Knaben results whose magnet link carried the info-hash as its last parameter, or carried no display-name parameter, were dropped row by row. The hash is now matched by its own alphabet regardless of what follows it, and the release name falls back to the row's own title column, so those results are kept.
-CHANGE: the DMM scraper is disabled by default. Its API answers HTTP 429 "Rate limit exceeded" to the very first request of a session, so it is effectively closed to third parties and was contributing zero sources while still costing a request and a timeout on every search. Nothing is lost: DMM's content still reaches you through Zilean, which indexes DMM's public hashlists. A one-shot migration turns the provider off on existing installs; the toggle stays visible under Scrapers, so if DMM ever relaxes the limit you can re-enable it with one click and it will not be switched off again.
