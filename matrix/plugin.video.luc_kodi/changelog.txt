[B][COLOR ff00fa9a]Version 1.0.56[/COLOR][/B]
-Scraper DMM it's available again:
-FIX: a TV search could lose every DMM result before a single link was read. The scraper asked for the show's season count as a required field, and when the caller did not supply it the whole search was abandoned - not just the season-pack detection that actually needed it. The field is now optional: packs are skipped when it is missing, single episodes and movies are unaffected, and the rest of the results come through as normal.
-CHANGE: the queue that spaces out DMM requests no longer holds other searches back while one request is in flight. It used to keep its turnstile locked for the entire round trip, so a second scraper thread could sit waiting up to seven seconds for a request that was not even its own. The turn is now reserved up front and released immediately, which spaces requests exactly the same way DMM measures them while letting the rest of the panel get on with its work. Three simultaneous searches finish about a third faster.
-FIX: a dropped connection or a slow network no longer fills kodi.log with a full stack trace. Timeouts and connection errors are now recognised for what they are and noted in the debug log in one line, the same as the other DMM outcomes. Genuine faults still report in full.
-NEW: "Deep search (2nd page, slower)" under Scrapers > dmm, off by default. DMM serves its results in pages, and the addon reads the first one - which already carries everything the panel needs for almost every title. Turning this on reads a second page as well for titles that filled the first, adding roughly a hundred more candidate releases at the cost of about two extra seconds per search. The second page is requested in turn, never alongside the first, so it cannot trip the rate limit.
-CHANGE: the DMM scraper is switched back on. Version 1.0.54 disabled it after its API replied HTTP 429 "Rate limit exceeded", which looked like the service closing its doors to third parties. It is not: DMM caps its torrent endpoint at one request every two seconds per IP address, and that cap is applied before the request is even looked at. The scraper was asking for two pages of results at the same time, so the second one was rejected on every single search - and, because the rejection arrives before anything else is checked, it also hid the fact that the rest of the scraper was working correctly.
-CHANGE: DMM now makes a single request per search instead of two, and those requests are queued so two of them can never overlap. If the limit is still hit - for example when you search again within two seconds - the scraper waits exactly as long as DMM asks and tries once more before giving up quietly. A search that DMM can answer returns up to a hundred results, the same as before, since the first page already carries everything the panel needs.
-CHANGE: DMM failures are now reported for what they are. A title DMM has not indexed yet is logged as such (it gets queued at their end and usually answers on your next search for it), a rejected request is logged as a rate-limit hit, and an authentication error points at the two things that can cause it - a device clock more than five minutes off, or a change on DMM's side. No more single catch-all warning that made every different problem look identical.
-NOTE: a one-shot migration turns the provider back on for installs where version 1.0.54 switched it off. After that the toggle under Scrapers is yours again and will not be touched.
[B][COLOR ff00fa9a]Version 1.0.55[/COLOR][/B]
-FIX: the catalog refresh at start-up (and its notification) was being postponed by five minutes on every single boot, so widgets kept showing stale content and the "Completed" notification never appeared when expected. The service skips a cycle while a video is playing - sensible during real viewing - but many skins play a short intro clip when Kodi starts, and the service's first check lands right inside it. The skipped cycle then waited the full five-minute interval before looking again. While the start-up refresh is still pending the service now re-checks every 15 seconds instead, so it runs as soon as the intro ends. The guard itself is unchanged for actual playback: once the start-up refresh is done, checks go back to every five minutes and never compete with a stream.
[B][COLOR ff00fa9a]Version 1.0.54[/COLOR][/B]
-CHANGE: catalog auto-update now finishes in about 2 seconds instead of 6-7. Every Kodi start used to invalidate the cached metadata of everything visible on page 1 of the nine TMDB lists (around 180 titles) and re-download each title's full details before the grid counted as fresh. Start-up now runs a light cycle: the nine list requests are re-read (so titles entering or leaving each list are still detected) and the visible fields of the grid - poster, fanart, rating, votes, plot and dates - are refreshed for already-cached titles straight from the list response, with no per-title detail requests at all. Only genuinely new titles download their full details at start-up.
-NEW: "Full metadata refresh at most every (hours)" setting (default 12) in the TMDB Catalog Update section. The heavy cycle that re-downloads full details - cast, logos, alternative posters, certifications, trailers - still runs, but at most once per this interval instead of on every single start, and also during long sessions when the interval elapses. Nothing is lost: info dialogs keep exactly the same data as before, refreshed on a schedule rather than on every boot.
-CHANGE: Tools > "TMDB: Update Catalog (Precache)" is now a guaranteed full refresh - it re-reads the lists AND re-downloads full metadata immediately, whenever you want everything fresh without waiting for the schedule.
-FIX: the "Check interval (hours)" setting was read as its position in the list rather than the hours it displays, so "6" actually checked every 2 hours. Both interval settings now map to real hours.
-FIX: resume points were silently lost for any title whose name contains double quotes. The bookmark lookup and cleanup pasted the title straight into the database query, so a quoted title broke it (visible in kodi.log while merely scrolling a list containing such a title). Both queries are now parameterized, so any title resolves and stores its resume point correctly.
-FIX: playback failed with "Playback not supported" when the chosen release was packed as a multi-part archive. Parts such as .z01/.z03, .r00, .part01.rar or .001 were missing from the invalid-extension lists and, being huge, won the largest-file selection - so the player received a fragment of an archive instead of a video. A shared check now filters them out for Premiumize, AllDebrid and the AllDebrid cloud browser, and the real video file inside the release is picked instead. Legitimate video files, including .ts and .m2ts, are untouched.
-FIX: MDBList ratings were never applied to TV shows in the source-selection panel. The lookup always used the movie route, so for a series MDBList replied 404 and every rating slot it should have filled (IMDb, TMDB, Trakt, Letterboxd and the rest) was left to the slower fallback. The route now follows the media type, so shows and episodes get their MDBList ratings just like movies.
-FIX: Knaben results whose magnet link carried the info-hash as its last parameter, or carried no display-name parameter, were dropped row by row. The hash is now matched by its own alphabet regardless of what follows it, and the release name falls back to the row's own title column, so those results are kept.
-CHANGE: the DMM scraper is disabled by default. Its API answers HTTP 429 "Rate limit exceeded" to the very first request of a session, so it is effectively closed to third parties and was contributing zero sources while still costing a request and a timeout on every search. Nothing is lost: DMM's content still reaches you through Zilean, which indexes DMM's public hashlists. A one-shot migration turns the provider off on existing installs; the toggle stays visible under Scrapers, so if DMM ever relaxes the limit you can re-enable it with one click and it will not be switched off again.
